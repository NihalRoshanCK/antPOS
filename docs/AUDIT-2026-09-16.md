# antPOS — Full Code Audit & Performance Report

**Date:** 2026-09-16
**Scope:** `apps/ant_pos` @ `a3c71d6` (branch `develop`), app version `0.0.2`
**Stack:** Frappe 15.83.0 + ERPNext (required, **not installed in this bench**), Vue 3.5 / Pinia / frappe-ui 0.1.146 / Vite 5 / Tailwind 3.4
**Size:** ~1,460 LOC Python, ~4,360 LOC Vue/JS, 16 whitelisted endpoints, 7 DocTypes, 10 Custom Fields

## Method & limits

This bench has **no site** and **ERPNext is absent**, so the app cannot be booted here. Everything below is
static analysis of source plus direct measurement of the committed production bundle in
`ant_pos/public/antPOS/`. Runtime numbers (p95 scan latency, DB time) are **not** measured — see
"Benchmarks to run" at the end.

# 2. P0 — Blockers

### P0-1 `save_fields_layout` is an unauthenticated-tier write primitive
`ant_pos/ant_pos/doctype/antpos_fields_layout/antpos_fields_layout.py:142`

```python
@frappe.whitelist()
def save_fields_layout(doctype: str, type: str, layout: str):
    ...
    doc.save(ignore_permissions=True)
```

Whitelisted, no role check, `ignore_permissions=True`. **Any** authenticated user — including a Website
User with no POS role — can create or overwrite any `Antpos Fields Layout` record and thereby change
which fields every cashier sees. Companion readers `get_fields_layout` (line 15) and `get_doc_field`
(`api/__init__.py:108`) also take an arbitrary `doctype` with no permission check and return full field
metadata / `frappe.new_doc(...).as_dict()` defaults for **any** DocType in the system.

**Fix:** require `frappe.only_for("System Manager")` on the writer; add
`frappe.has_permission(doctype, "read", throw=True)` on both readers; drop `ignore_permissions`.

### P0-2 `scan_barcode` leaks item cost data to every cashier
`ant_pos/ant_pos/api/item.py:49, 64, 79, 104` — four code paths do:

```python
barcode_data["item"] = frappe.db.get_value("Item", item_code, ["*"], as_dict=True)
```

`["*"]` returns every Item column, including `valuation_rate`, `last_purchase_rate`, `standard_rate`,
`is_purchase_item` and all custom fields. A POS Cash user scanning a barcode receives your landed cost.

**Fix:** enumerate the ~15 fields the UI actually consumes.

### P0-3 `get_users` exposes the full user directory
`ant_pos/ant_pos/api/session.py:3` — whitelisted, no permission check, returns `name`, `email`,
`full_name`, `user_type`, `enabled` for **every** User row. Account enumeration for anyone who can log in.
It is called with `auto: true` from `stores/users.js`, so it fires on every app load.

**Fix:** it is only ever used to render the current user's avatar in `Sidebar.vue`. Replace with a
single-user lookup, or gate behind `frappe.has_permission("User", "read")`.

### P0-4 `calculate_invoice_item_taxes` instantiates arbitrary client-supplied documents
`ant_pos/ant_pos/api/sales_invoice.py:8`

```python
invoice = frappe.get_doc(doc)              # doctype comes from the client
invoice.flags.ignore_permissions = True
invoice.set_missing_values()
```

The client controls `doctype`. Nothing pins it to `Sales Invoice`, and permissions are explicitly
disabled before controller code runs. Nothing is persisted, but `set_missing_values()` on an arbitrary
controller is a side-effect surface.

**Fix:** `doc["doctype"] = "Sales Invoice"` before `get_doc`, and drop the `ignore_permissions` flag —
the caller must have create permission on Sales Invoice anyway.

### P0-5 Production sourcemaps ship your source code
`AntPos/vite.config.mjs:18` sets `sourcemap: true` in `buildConfig`. The result: **22 `.map` files,
11 MB**, committed and served from `/assets/ant_pos/antPOS/assets/*.map`. Anyone can reconstruct the
unminified frontend including comments.

**Fix:** `sourcemap: false` for the shipped build (or `'hidden'` and upload maps to an error tracker);
delete the committed maps.

### P0-6 `items()` crashes or corrupts serial numbers on the main scan path
`ant_pos/ant_pos/api/item.py:215`

```python
"serial_no": "\n".join(selected_serial_no),
```

`selected_serial_no` is a **string or None**, never a list:
- Plain item (no serial): `search_values.get("serial_no")` is `None` → `"\n".join(None)` →
  `TypeError: can only join an iterable` → HTTP 500 on **every non-serialised item scan**.
- Serial item: `"\n".join("SN001")` → `"S\nN\n0\n0\n1"` — the serial is exploded into characters.

**Fix:** `"\n".join(selected_serial_no) if isinstance(selected_serial_no, list) else (selected_serial_no or "")`.

### P0-7 `scan_barcode` returns a tuple on the not-found path
`ant_pos/ant_pos/api/item.py:113` — note the trailing comma:

```python
return "No matching item found. Please check the barcode, ...",
```

That is a 1-tuple, not a string. Callers get `["No matching item found..."]` after JSON serialisation while
`http_status_code` is 404; `ItemSelector.vue:37 onSuccess(data)` then reads `data.serial_no` off it.

**Fix:** `frappe.throw(_("No matching item found..."), frappe.DoesNotExistError)` — let the frontend's
existing `onError` toast handle it.

### P0-8 Tenant-specific GL accounts hardcoded in the shipped bundle
`AntPos/src/components/Payment.vue:379-380`

```js
paid_from: 'Debtors - FITPL',
paid_to:   "MGR Cash - FITPL",
```

Verified present in the built artifact (`public/antPOS/assets/Payments-D2mgv-Pl.js`). The Payments screen
cannot work for any company whose abbreviation isn't `FITPL`, and silently books to the wrong ledger if
another company happens to share it.

**Fix:** derive `paid_from` from the customer's receivable account and `paid_to` from
`Mode of Payment Account` for the selected company — the server-side hook in
`api/payment_entry.py:4` already does exactly this; just stop sending the fields.

### P0-9 `Ant Closing Shift` declares `amended_from` twice
`ant_pos/ant_pos/doctype/ant_closing_shift/ant_closing_shift.json` — the `fields` array contains two
`amended_from` entries. Frappe rejects duplicate fieldnames on `bench migrate` in strict mode and
produces undefined column behaviour otherwise.

**Fix:** delete the duplicate, add a patch to clean up existing installs.

# 3. P1 — High

### P1-1 Close Shift cannot be saved
`ant_closing_shift.json` marks `pos_profile` as `reqd: 1`, but `AntClosingShift.validate()`
(`ant_closing_shift.py:6-34`) never sets it, and `CloseShift.vue:76-84` sends only
`doctype`, `payment_reconciliation`, `ant_opening_shift`. Mandatory-field validation fails on save.
**Fix:** `self.pos_profile = opening_shift_doc.pos_profile` alongside the existing `self.company` assignment.

### P1-2 `get_opening_shift()` queries a column that doesn't exist
`ant_closing_shift.py:37-42` filters `Ant Opening Shift` on `{"user": self.user}`. That DocType's field is
`cashier`. Raises a SQL error whenever `ant_opening_shift` is blank.

### P1-3 Every return reuses one hardcoded document name
`AntPos/src/components/Dialog/Return.vue:146`

```js
invoiceStore.invoice = { ...runDoCMethod.data.docs[0], status: null, name: "new-sales-invoice-jpodtuhocv" }
```

A literal temp name shared by every return in every session. `Held.vue` and `stores/pos.js` correctly use
`generateTempName()`; this one was missed. Two concurrent returns collide in the client doc cache.

### P1-4 Print and follow-up payments use the pre-save temp name
`AntPos/src/components/Invoice.vue:105,128,132`

```js
let invoice = { ...invoiceStore.invoice };   // snapshot BEFORE save — name is "new-sales-invoice-…"
...
createPayments(invoice);                     // Payment Entry references a non-existent invoice
createPrint(invoice.name);                   // /printview?name=new-sales-invoice-…  → 404
```

`saveAndSubmit()` writes the server response into `doc.value.doc`, never back into `invoice` or the store.
**Fix:** read the name from `doc.value.doc.name` after submit.

### P1-5 Three unbounded list queries
`pageLength: Number.MAX_VALUE * 2` evaluates to `Infinity`:

| File | Query |
|---|---|
| `components/Customer.vue:44` | **every** non-disabled Customer, with `mobile_no`/`group`/`territory` |
| `components/Payment.vue:42` | **every** open Sales Invoice (`outstanding_amount > 0`) |
| `components/Item.vue:48` | **every** Serial No for the item, per cart line |

`Payment.vue:42` also silently overrides a `pageLength: 20` set 14 lines earlier in the same object literal.
At 50k customers this is a multi-MB JSON payload on app open, then `Autocomplete.filterOptions()`
(`custom_components/Autocomplete.vue:108`) re-scans the whole array on every keystroke before
`slice(0, 50)` throws 99% of it away.

**Fix:** server-side search — `pageLength: 20` plus a debounced `like` filter, which is what
`Return.vue`/`Held.vue` already do correctly.

### P1-6 `get_user_permissions` aggregates roles incorrectly
`ant_pos/ant_pos/api/__init__.py:49-68`

```python
custom_perms = frappe.get_all("Custom DocPerm", filters={"parent": doctype, "role": ["in", user_roles], permtype: 1}, fields=["if_owner"])
if custom_perms:
    return custom_perms[0]["if_owner"] == 1
```

Returns the `if_owner` flag of an **arbitrary first row**. A user holding both an unrestricted role
(`if_owner=0`) and a restricted one (`if_owner=1`) gets a result that depends on row ordering. Should be
`all(p.if_owner for p in perms)` — owner-restricted only if *every* granting role is restricted.

### P1-7 `Customer.vue` watcher never fires
`components/Customer.vue:105`

```js
watch(usePosProfileStore().hasNoData, (newVal) => { customerResource.reload() }, { immediate: true })
```

Pinia unwraps refs on store access, so the watch source is a plain `false`, not a reactive source. Vue
warns and the callback runs only once via `immediate`. The customer list is never refreshed when a shift
opens. `App.vue:38` gets this right with `() => posProfileStore.hasNoData`.

### P1-8 `get_sidepanel_sections` is dead on arrival
`antpos_fields_layout.py:63` — `frappe.get_doc("CAntpos Fields Layout", ...)` (leading `C` typo). Always
raises `DoesNotExistError`. Also note the function builds `fields_meta` (line 89-91) and never uses it.

### P1-9 Opening-shift validation is inert and non-reentrant
`ant_opening_shift.py:9-21`
- The `period_start_date` vs `period_end_date` check is guarded by `if self.posting_date:` — which is
  always `None` on a new doc, and is unconditionally overwritten to `today()` two lines later. The check
  never runs on the path that matters.
- `get_openingshift_for_user()` doesn't exclude `self.name`, so any re-validate of an already-open shift
  (amend, or a future `on_update`) throws.
- User-facing strings: `"casher already as a open shift"`, `"Posting Date is  cannot be grater than  Period Start Date "`.

### P1-10 Batch key mismatch in the cart row
`components/Item.vue` uses two different keys against the same `get_batch.data` payload:
`getbatchNo()` (line 91) reads `batch_no.batch_id`, while the `selected_batch_no` watcher (line 115) reads
`b.batch_no`. One of them is silently `undefined` — batch dropdown labels or stock/expiry lookup is broken.
Confirm against `erpnext.stock.doctype.batch.batch.get_batches`'s actual return shape.

### P1-11 Closing a shift leaves the link field empty
`ant_closing_shift.py:108-111` sets the opening shift's `status` to `Closed` but never populates
`ant_closing_shift_detail`. `pos_profile.get_openingshift()` filters on **both**
(`ant_closing_shift_detail in ["", None]` and `status == "Open"`), so the field is permanently dead weight
and the audit trail from opening → closing document is missing. There is also no `on_cancel` to reopen a
shift when a closing entry is cancelled.

**Service worker precache:** 17 entries ≈ 2.4 MB (JS/CSS/HTML). Fonts are correctly left out. ✅

### Critical path
Initial load blocks on a **2.1 MB single JS chunk**. On a typical 4 Mbps in-store connection that is
~4 s of transfer before Vue boots, plus a 131 KB render-blocking stylesheet. Then, in parallel on mount:
`get_translations` (full translation dict), `get_users` (**every** user), `get_user_permissions`
(6 `frappe.get_all` + 9 `has_permission` calls), `get_openingshift`, `AntPOS Settings`, and
`Customer.vue`'s **unbounded** customer list.

### Recommended build changes (`AntPos/vite.config.mjs`)
1. `sourcemap: false` → **−11 MB**, and closes P0-5.
2. Subset Inter to `Regular/Medium/SemiBold/Bold` woff2 only → **−8 MB**, ~−7.9 MB of deployed assets.
   Even better, use the variable font `Inter.var-C9xDBOS3.woff2` alone.
3. `build.rollupOptions.output.manualChunks` splitting `vue`/`vue-router`/`pinia` from `frappe-ui` from
   app code → the 2.1 MB chunk becomes 3 cacheable chunks; app-only redeploys stop invalidating vendor.
4. Add `build.reportCompressedSize` and a size budget to CI.

**Projected:** 23 MB deployed → **~3.2 MB**; initial JS 2.1 MB → ~600 KB app + ~1.4 MB vendor (cached
across releases).

## 4.2 PWA is non-functional

Three independent defects, all verifiable in the committed artifacts:

1. **Scope never matches the app.** `public/antPOS/registerSW.js` registers with
   `{ scope: '/assets/ant_pos/antPOS/' }`, but the app is routed at `/antPOS`
   (`hooks.py:233`, `router.js:24`). A service worker cannot control pages outside its scope — **offline
   mode has never worked.**
2. **Manifest is invalid.** `manifest.webmanifest` has `"scope": "/assets/ant_pos/antPOS/"` with
   `"start_url": "/antPOS"`. `start_url` outside `scope` → Chrome rejects the manifest → **the app is not
   installable.**
3. **Every icon 404s.** `ant_pos/public/manifest/` **does not exist**. `index.html` references it 32 times
   (1 apple-touch-icon + 30 splash screens); the manifest points somewhere else again
   (`/assets/antPOS/manifest/…` — wrong app slug). That is ~32 failed requests per cold iOS load and no
   installable icon anywhere.

**Fix:** serve `sw.js` from a path whose scope covers `/antPOS` (or send
`Service-Worker-Allowed: /antPOS`), set `scope: '/antPOS'` + `start_url: '/antPOS'` in the manifest, and
either add the icon assets under `ant_pos/public/manifest/` or strip the dead references from `index.html`.

## 4.3 Query-level hot spots

| # | Location | Problem | Fix |
|---|---|---|---|
| Q1 | `api/item.py:42-109` `scan_barcode` | Up to **4 sequential** `get_value` probes (Item Barcode → Serial No → Batch → Item), then a 5th `["*"]` Item fetch. Worst case 5 round-trips per scan. | Single `UNION ALL` or resolve identifier type client-side from the scanned prefix |
| Q2 | `api/item.py:153-248` `items()` | **3 raw SQL aggregations over `tabStock Ledger Entry`** per add-to-cart (batch list, batches-with-qty, batch qty re-check) — two of which compute overlapping sums | Collapse to one grouped query; reuse the result |
| Q3 | `components/Item.vue:291-295` | Per cart line `onMounted` fires `get_batches_list` **and** an unbounded Serial No list → **N+1 per line**. A 20-line sale = 40 extra requests | Hoist to a cart-level batch fetch keyed by item_code; lazy-load serials only when the serial picker opens |
| Q4 | `api/pos_profile.py:50-62` | N+1: one `POS Payment Method` query **per POS Profile** | Single `get_all` with `parent in [...]`, group in Python |
| Q5 | `ant_closing_shift.py:48-60` | `LEFT JOIN tabSales Taxes and Charges` fans out to one row per (invoice × tax line), then de-dupes in Python via `seen_invoices` | Two separate queries: invoice totals, then tax aggregation |
| Q6 | `api/payment_entry.py:13-35` | 2 unindexed scans keyed on `si.custom_ant_opening` (a Custom Field — **no index by default**) | Add an index on `Sales Invoice.custom_ant_opening`; it is the join key for both shift close and payments |
| Q7 | `www/antPOS.py:13` | `frappe.db.commit()` on **every** page render, before any write | Delete it |
| Q8 | `api/__init__.py:98` `get_translations` | `allow_guest=True`, returns the full translation dict, no HTTP cache header | Add `Cache-Control` + ETag keyed on language |

**Q6 is the highest-leverage single change** — one index fixes both the Close Shift and Payments screens.

## 4.4 Frontend render behaviour

`components/Item.vue` registers **six** watchers (`selected_batch_no`, `selected_serial_no`,
`price_list_rate`, `qty`, `discount_percentage`, `rate`), and four of them call `validateInvoice()` →
`emitter.emit('calctotal')` → `ItemSelector.calculateAmountTotal()` → a POST to
`calculate_invoice_item_taxes` that serialises **the entire invoice** and rebuilds a full `Sales Invoice`
document server-side.

Debounce is 500 ms (`ItemSelector.vue:173`), so bursts coalesce — but changing a rate on line 1 of a
20-line cart still cascades: `rate` watcher → `calculateRateTotal` → `calculateAmountTotal` +
`discount_amount` write → `validateInvoice`. And `Item.vue:232` deep-clones the serial array with
`JSON.parse(JSON.stringify(...))` inside a watcher.

**Recommendation:** replace the emitter fan-out with a single `watchEffect` over a computed cart
fingerprint (item_code, qty, rate, discount, batch, serial-count), and compute line totals locally —
only call the server when taxes or pricing rules can actually change.

# 5. P3 — Hygiene

- **No tests.** All four `test_*.py` files are empty `FrappeTestCase` subclasses with `pass`. CI
  (`.github/workflows/`) only runs `bench build --app ant_pos` — it never installs the app on a site,
  never runs `bench migrate`, and never executes a test. The duplicate `amended_from` (P0-9) would have
  been caught by a single migrate step.
- **Dead code:** `AntPos/src/components/SalesInvoice.vue` is entirely commented out (and ends with a stray
  `</script> -->` plus an empty `<template>`), references CRM columns, and is imported nowhere.
  `ant_pos/ant_pos/utils/employee.py` is 0 bytes. `utils.is_employee()` is only referenced from a
  commented-out block in `ant_opening_shift.py:20-21`.
- **23 MB of build output committed to git** (`ant_pos/public/antPOS/`), including the 11 MB of sourcemaps.
  `.gitignore` ignores `AntPos/public/` but not `ant_pos/public/antPOS/`.
- **`package.json:8`** passes `--base=/assets/ant_pos/AntPos/` (capital `A`) while the real serve path is
  `/assets/ant_pos/antPOS/`. It happens to be harmless because the `frappeui()` plugin's `buildConfig`
  overrides it — but it is a trap for the next person.
- **Dangling fixture reference:** `custom_field.json` inserts `custom_create_sales_order` after
  `custom_close_letter_head`, which no fixture creates.
- `patches.txt` is empty; there is no migration path for any of the schema fixes above.
- `AntPOS Settings` grants write to System Manager only, but `Sidebar.vue:48-54` shows the Settings dialog
  to every user — non-admins get a permission error on save.
- `posprofile_user_query_conditions` (`api/__init__.py:33`) special-cases a role named `"Administrator"`.
  Frappe has no such role — Administrator is a *user*. Harmless (it holds every role anyway) but misleading.
- 5 stray `console.log`/`console.error` calls in shipped frontend code.

Found and fixed while in the code, not in the original audit:

- `get_payments` had no `docstatus` filter on Payment Entry, so **draft and
  cancelled payments counted toward shift closing totals**.
- The payment hook read `paid_from`'s currency and stored it against `paid_to`.
- `Mode of Payment Account` was looked up without a company filter, returning
  whichever company sorted first.
- Advance Payment Entries carried no `reference_no`, so `get_pos_payments` never
  saw them and they were missing from every shift close.
- `Customer.vue`'s customer-group restriction was captured before the POS profile
  loaded and was therefore always empty — cashiers saw every customer regardless
  of the profile's `customer_groups`.
- `getbatchNo()` dereferenced `get_batch.data` before the fetch resolved; it only
  survived because the line-detail block is collapsed by default.
- CI cloned the app from GitHub instead of testing the checked-out ref.
- A failed customer creation was only `console.error`'d — the cashier saw nothing.

## Outstanding

**D1 needs a change outside the app.** The service worker is now registered with
scope `/antPOS/`, but the browser will not grant a wider-than-default scope
without a `Service-Worker-Allowed` response header, which cannot be set from
inside a Frappe app. The nginx snippet is in `docs/DEPLOYMENT.md`. Until it is
added there is no offline shell — everything else works, and the manifest is now
valid so the app is installable.

**B7 — batch key mismatch (P1-10), RESOLVED.** Checked against erpnext
`version-15` source: `get_batches()` returns only `{batch_id, qty}` and no expiry
date at all. So `getbatchNo()` was right and the watcher was wrong — `b.batch_no`,
`batch.stock_qty` and `batch.expiry_date` were all `undefined`, which means
**selecting a batch always zeroed the displayed available quantity and cleared the
expiry date**. Root cause was two shapes for one concept: `items()` returns
`{batch_no, expiry_date, stock_qty}` while `get_batches_list` passed erpnext's
shape straight through. `get_batches_list` now returns the `items()` shape, and
the client has a single contract.

Two further defects found while building the fixtures:

- **`Ant Payment Entry Reference` field mismatch.** The child table has `date`,
  `amount`, `mode_of_payment`, but `get_pos_payments` selected `posting_date`,
  `paid_amount`, `payment_type`. `Document.append()` silently drops unknown keys,
  so **every row in a closing shift's payment table was blank apart from the
  reference**. Fixed with SQL aliases.
- **`POS Profile.skip_printview` does not exist.** `Invoice.vue` gates the print
  window on `store.posProfileData?.skip_printview`; it is neither a standard
  field nor in `custom_field.json`, so it is always `undefined` and the setting
  has never had any effect. Left as-is: it needs a product decision on whether to
  add the custom field or remove the feature. `custom_edit_rate` is the mirror
  case — shipped as a custom field but referenced nowhere in the frontend, which
  uses the standard `allow_rate_change` instead.

**C7 — `Item.vue` watcher consolidation, deliberately not attempted.** Six
watchers each call `validateInvoice()`, which round-trips the whole invoice to
`calculate_invoice_item_taxes`. Collapsing them into one fingerprint watcher is
the right fix, but it is a rewrite of live pricing and discount logic and I have
no way to verify it without a running POS. Specification is in §4.4.

**Vendor chunk, ~1 MB of dead weight.** The `vendor` chunk is dominated by
frappe-ui's transitive dependencies — the prosemirror/tiptap editor stack,
lowlight/highlight.js, chart.js, tippy. This app imports none of them; they
arrive through the `frappe-ui` barrel import. Deep-importing the ~25 components
actually used (`frappe-ui/src/components/...`) would drop roughly 1 MB, but it is
a wide, fragile refactor that should be done with the app running in front of you.

**Other known-but-untouched items:** the dangling `custom_close_letter_head`
reference in `custom_field.json`; `AntPOS Settings` being writable only by System
Manager while the Settings dialog is in every user's sidebar; the
`"Administrator"` role special-case in `posprofile_user_query_conditions`; and
the mixed tab/space indentation throughout the Python (a formatter pass).
